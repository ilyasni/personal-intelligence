# Агентская архитектура разработки

PIL разрабатывает один человек + три AI-агента. Каждый агент имеет разные tool-capabilities, разный способ инвокации, разную «среду обитания» — но **читает ту же документацию** в `docs/` и решает **те же тикеты** из [../09-roadmap/milestones.md](../09-roadmap/milestones.md).

Этот документ — про то, как устроен каждый агент, чтобы любой из них быстро встроился в работу проекта без потери контекста, и чтобы человек мог осознанно переключаться между ними.

## Общая модель

```
┌──────────────────────────────────────────────────────────────────┐
│                            Owner                                  │
│  выбирает агента под задачу и переключается между сессиями        │
└─────────────────────────┬────────────────────────────────────────┘
                          │
       ┌──────────────────┼──────────────────┐
       │                  │                  │
┌──────▼──────┐    ┌──────▼──────┐    ┌──────▼──────┐
│ Claude Code │    │   Codex     │    │   Cursor    │
│ CLAUDE.md   │    │  AGENTS.md  │    │ .cursorrules│
└──────┬──────┘    └──────┬──────┘    └──────┬──────┘
       │                  │                  │
       └────────────┬─────┴──────────┬───────┘
                    │                │
                    ▼                ▼
        ┌─────────────────────────────────────┐
        │   docs/  — общая документация,      │
        │   репозиторий и тикеты              │
        │   единые для всех агентов           │
        └─────────────────────────────────────┘
```

Все три агента читают `docs/` целиком. Основные различия — в:

1. **Точке входа.** `CLAUDE.md`, `AGENTS.md`, `.cursorrules` — короткие файлы, которые конкретный агент подсасывает автоматически. Содержат: миссию, сильные стороны конкретного агента, стартовый чек-лист, минимум конвенций.
2. **Способе работы.** Claude Code — диалоговый агент с длинным контекстом; Codex — автономные runs в CLI/cloud; Cursor — интерактивный редактор.
3. **Что лучше делать у каждого** — см. [when-to-use-which.md](when-to-use-which.md).

## Точки входа агентов

### Claude Code → `CLAUDE.md`
- Подсасывается автоматически при старте сессии Claude Code в репо.
- Содержит миссию + сильные стороны + первые 5 шагов + ключевые конвенции + список команд + ссылку на playbook (этот файл).
- Видит весь `docs/` через файловые tools (Read/Glob/Grep).

### Codex → `AGENTS.md`
- Подсасывается Codex CLI / Codex cloud при старте.
- Тот же блок миссии (общая часть), но «сильные стороны» подсвечивают batch-задачи.
- При работе в фоновом режиме (без чата) — handoff-блок в PR обязателен.

### Cursor → `.cursorrules`
- Используется Cursor IDE.
- Кратче, чем CLAUDE.md/AGENTS.md, потому что Cursor подбирает контекст из открытых файлов сам.
- «Сильные стороны» — UI и интерактивная правка.

Все три файла:
- ссылаются на одни и те же `docs/`;
- держат общий one-pager проекта;
- повторяют общие конвенции в адаптированном под агента виде;
- содержат agent-specific примеры команд и оговорки по среде.

Формулировки в них не обязаны быть побуквенно идентичными. Источник правды — `docs/11-agents/*` плюс актуальные ops-доки.

## Актуальная среда выполнения

На 2026-05-12 нужно различать две среды:

1. **Документационный checkout.** Здесь лежат `docs/`, roadmap, точки входа агентов и корневой `Makefile`.
2. **Server runtime.** Сервер `ilyasni@192.168.31.165`, директория `~/pil`, где реально поднимается compose-стек и запускаются сервисы.

Важно:

- server runtime сейчас живёт на одной VM `personal-intelligence`;
- в `~/pil` сейчас нет `.git`, `docs/` и корневого `Makefile`;
- часть документации описывает **целевое состояние** (две VM, полный PR/CI flow, расширенные make-обёртки), а не уже реализованную инфраструктуру.

## Что делает агент при старте сессии

Универсальный чек-лист (применяется любым из трёх):

1. Прочитать свою точку входа.
2. Прочитать [agent-architecture.md](agent-architecture.md) (этот файл) и [shared-conventions.md](shared-conventions.md).
3. Прочитать [handoff-protocol.md](handoff-protocol.md) — даже если ты ничего не передаёшь, в обратной стороне ты можешь принять работу.
4. Сверить статус по [../09-roadmap/milestones.md](../09-roadmap/milestones.md).
5. Если есть открытый тикет/PR/hand-off note с пометкой «hand-off to <my-agent>» — взять.
6. Иначе — взять следующий unassigned в текущем sprint.
7. Перед первым коммитом или handoff — `make verify`, если работа идёт в полном checkout; на сервере без корневого `Makefile` — прогнать эквивалентные команды вручную или явно зафиксировать, что проверка не запускалась.

## Что делает агент при завершении

См. [handoff-protocol.md](handoff-protocol.md). Минимум: заполнить handoff-блок в PR/таске.

## Переключение агентов в середине работы

Owner может (и должен) переключаться, когда задача сменила природу:

- Архитектурная развилка появилась в середине batch — закрыть Codex, открыть Claude Code, обсудить, написать ADR, потом продолжить Codex'ом.
- Backend готов, осталась UI-доводка — закрыть Claude Code, переключиться на Cursor.
- Перед релизом — Cursor доводит UI, Codex параллельно прогоняет load test и обновляет dependencies.

Правила:
- Любое переключение — через PR/коммит с handoff-блоком; если текущая server working copy без git, то через handoff-файл и апдейт `milestones.md`.
- Никаких «в чате договорились, забыли в коде» — фиксируем письменно в репо.

## Когда какой агент НЕ подходит

- **Claude Code.** Не для batch-прогонов по 50 PR. Не для UI-полировки с превью.
- **Codex.** Не для тонких архитектурных дискуссий с человеком в реальном времени. Не для UI с моментальным feedback'ом.
- **Cursor.** Не для длинных автоматических runs. Не для сквозных рефакторов через 20 файлов без участия пользователя.

См. подробности — [when-to-use-which.md](when-to-use-which.md).
