# ADR 0006: Маленький monorepo с автономными сервисами (не monolith, не microservice-zoo)

- Дата: 2026-05-11
- Статус: Accepted

## Контекст

PIL — личный self-host. Сервисов задуман десяток (ingestor + extractors + api + maintenance + ui). Нужно решить: один процесс или много.

## Варианты

**A. Монолит (один FastAPI + background tasks).**
+ Минимум операций.
+ Быстро запускается.
− Невозможно масштабировать одну отдельную функцию (например, summarizer с тяжёлым LLM).
− Сложнее изолировать ошибки одного pipeline от других.
− Один процесс с долгими async-консьюмерами — сложнее наблюдать.

**B. Полноценные microservices (k8s-style).**
+ Полная изоляция и масштабирование.
− Overhead на эксплуатацию для одного пользователя.
− Нужны service discovery, service mesh.
− Долгий boot, тяжёлый CI.

**C. Monorepo + автономные сервисы (один процесс на сервис, общий docker-compose).**
+ Каждый сервис — простой процесс, легко рестартить, легко тестировать.
+ Общая кодовая база, общие libs.
+ Можно мерджить два сервиса в один процесс, если оба маленькие (но это исключение).
− Чуть больше образов (но они тонкие, одна Python-база).
− Чуть больше healthchecks.

## Решение

**C — monorepo + автономные сервисы.**

Каждый сервис из `services/` — свой Dockerfile, свой entrypoint, свой образ. Общая база Python (`pil-base`) ускоряет билд.

Все сервисы используют единые `libs/*` без публикации в private package registry (path-зависимости в poetry).

## Правила

- Один сервис = одна ответственность из `docs/02-architecture/components.md`.
- Сервис не делает RPC к другому сервису. Только: события, БД, MCP/REST (через api).
- Можно «сложить» два сервиса в один процесс в dev-режиме (например, для отладки), но в проде они всё равно отдельные контейнеры.

## Последствия

- (+) Каждый сервис тестируется и деплоится независимо.
- (+) Низкий вход для нового agent'а — открыл один сервис, читаешь только его.
- (−) Чуть больше образов в registry.
- (−) Нужно следить, чтобы libs/* не превращались в гигантскую общую папку (мерить размер).
