# ADR 0001: Используем ADR для фиксации архитектурных решений

- Дата: 2026-05-11
- Статус: Accepted

## Контекст

Проект ведут три AI-агента и один человек. Решения должны быть:
- видимыми (а не «в голове»),
- сохраняемыми (за пределы сессии),
- ревьюабельными до реализации.

Без ADR агенты будут принимать архитектурные решения молча, и через 2 месяца невозможно будет восстановить, почему так.

## Решение

Все архитектурно влияющие решения фиксируются в ADR — короткие markdown-файлы в `docs/10-adr/` с нумерацией `NNNN-kebab-name.md`. Шаблон:

```
# ADR NNNN: Заголовок

- Дата: YYYY-MM-DD
- Статус: Proposed | Accepted | Deprecated | Superseded by ADR-XXXX

## Контекст
Что мы решаем и почему сейчас.

## Варианты
A) ...  
B) ...  
C) ...

## Решение
Какой вариант и почему.

## Последствия
Положительные и отрицательные. Что меняется в коде/доках/процессе.
```

## Когда обязательно открывать ADR

- Меняется контракт событий (`libs/contracts`).
- Меняется схема Postgres/Neo4j/Qdrant (несущая).
- Появляется новый сервис или ключевая библиотека.
- Меняется политика приватности.
- Меняется стек (новая БД, новый язык).
- Переключение мажорной версии библиотеки.

## Когда ADR не нужен

- Косметика, рефакторинг внутри сервиса без публичных контрактов.
- Изменения тестов.
- Документация без архитектурных решений.

## Процесс

1. Открыть PR с черновиком ADR (status `Proposed`).
2. Тегнуть owner-а на ревью.
3. После принятия — `Accepted` + ссылка из affected docs.
4. При устаревании — `Superseded by ADR-XXXX`.

## Последствия

- (+) Сохранённая историческая память архитектуры.
- (+) Любой агент в новой сессии понимает, почему сделано так.
- (−) Лёгкое замедление при первом введении изменений (минута на ADR).
